# PocketPet 技术选型评估

> 基于 `docs/01-调研报告.md`，对关键技术点做选型决策。

## 1. 选型总览

| 领域 | 决策 | 备选 | 理由 |
|---|---|---|---|
| Agent 框架 | **Google ADK Go v2**（`google.golang.org/adk/v2`） | langchaingo / 自研 | 需求明确指定；官方维护；tools/skills/MCP/A2A 生态完整 |
| LLM 抽象 | **`model.LLM` 接口 + provider 工厂** | 直连各家 SDK | ADK 原生抽象；新增提供商只需实现工厂 |
| OpenAI 兼容 | **`model/openaimodel`（Responses API）+ 自研 Chat-Completions 薄适配兜底** | huytd/adk-openai-go | 官方包优先；兜底适配层隔离第三方端点差异 |
| HTTP 服务 | **标准库 `net/http` + 轻量路由**（`chi` 或 Go 1.22+ ServeMux） | gin / echo | 依赖最少、嵌入式友好；无重框架需求 |
| 流式输出 | **SSE（Server-Sent Events）** | WebSocket | 单向推送足够（对话回复、状态事件）；对接前端最简单；嵌入式资源占用低 |
| 持久化 | **SQLite（`modernc.org/sqlite`，纯 Go）** | BoltDB / PostgreSQL | 单文件、零依赖、纯 Go 可交叉编译；关系模型适合宠物状态 |
| 配置 | **TOML/YAML 单文件 + 环境变量覆盖** | viper | 简单层级即可，不强依赖 viper |
| 扩展机制 | **三层：functiontool 插件接口 + ADK skilltoolset + MCP** | 进程外插件（hashicorp go-plugin） | 见第 3 节 |
| 日志/遥测 | `log/slog` + 预留 ADK `telemetry`（OTel） | zap | 标准库优先 |

## 2. Agent 框架评估：ADK Go v2

### 优点
- 官方维护，与 Python/TS/Java ADK 设计对齐，长期演进有保障。
- `llmagent` + `functiontool`：宠物操作以工具形式交给 LLM 调用，天然契合"Agent 驱动宠物行为"。
- `skilltoolset`：从磁盘加载 SKILL.md 形式的技能包，是需求 2 的直接答案。
- `mcptoolset`：接入任意 MCP Server，扩展能力无上限（查天气、控制智能家居喂食器等）。
- `session` / `memory` 服务：宠物与主人的长期记忆（"记得主人名字"）。
- 纯 Go、无 cgo，满足嵌入式目标。

### 风险与对策
| 风险 | 等级 | 对策 |
|---|---|---|
| v2 API 仍在演进，升级可能有 breaking change | 中 | ADK 相关代码全部收敛在 `internal/agent` 包内，核心业务包不 import ADK；升级影响面可控 |
| `openaimodel` 标记 Experimental，且仅支持 Responses API | 中 | provider 工厂内做适配分发；为 Chat-Completions-only 端点写薄适配层（实现 `model.LLM`，接口仅 2 个方法量级） |
| `openaimodel` 仅文本，不支持多模态 | 低 | MVP 只需文本；多模态留作路线图 |
| ADK 自带 REST server 与业务 API 形态不一致 | 低 | 不用官方 launcher，自建 API 层，内部直接调用 `runner.Run` |

## 3. 扩展机制选型（需求 2）

采用**三层扩展体系**，由轻到重：

1. **内置插件接口（Go interface 注册）** —— 编译期扩展
   - 定义瘦核心 `Plugin` + 可选能力接口集（`ToolProvider`、`TickHook`、`EventSubscriber`、`RouteProvider`、`SchemaProvider`、`Depender`、`Shutdowner`），装配时类型断言发现。早期草案中的 `OnAction`/`OnChat` 未落地——对话扩展走 Tool 注入即可。
   - 适合随主程序编译的核心扩展（如探险、交友）；YAML `plugins` 段可开关与调参，但不支持第三方二进制热插拔。
2. **Skill 包（SKILL.md，运行时加载）** —— ADK `skilltoolset`
   - 技能以目录形式放在 `skills/` 下，含 `SKILL.md`（指令 + 资源文件），运行时挂载为工具集。
   - 适合不改代码即可新增"人格化能力"（如讲睡前故事、节日彩蛋）。
3. **MCP（进程外 / 远程工具）** —— ADK `mcptoolset`
   - 适合接入外部世界能力；也为未来物理设备（舵机、传感器）预留通道。

明确**不采用** hashicorp go-plugin 这类 RPC 插件：二进制分发复杂、嵌入式场景过重，三层体系已覆盖需求。

## 4. 养成核心 vs LLM 的职责划分（关键决策）

| 职责 | 实现 | 理由 |
|---|---|---|
| 属性数值、衰减、成长、死亡规则 | **确定性 Go 代码**（领域层 + tick 引擎） | 养成逻辑必须可测试、可重现、离线可运行；不能交给 LLM 概率决策 |
| 交互动作的执行（feed/play/clean/sleep） | **领域层方法**，同时包装为 Agent 工具 | API 直接调用与 LLM 调用走同一条路径，行为一致 |
| 人格化表达（对话、情绪文案、主动关心主人） | **LLM Agent** | 这是 LLM 的核心价值；输入是当前状态快照，输出是文本/情绪标签 |
| 自主行为（到点喊饿、困了想睡） | tick 引擎产生事件 → 触发 Agent 生成表达 | 事件确定性，表达个性化 |

结论：**数值在 Go，灵魂在 LLM**。LLM 不可用时宠物核心功能照常运转（降级模式）。

## 5. 最终技术栈清单

- Go 1.24+（工具链稳定、ServeMux 增强）
- `google.golang.org/adk/v2`（llmagent / openaimodel / gemini / functiontool / skilltoolset / mcptoolset / session / memory）
- `github.com/openai/openai-go/v3`（openaimodel 依赖，兜底适配层复用）
- `modernc.org/sqlite`（纯 Go SQLite）
- `github.com/go-chi/chi/v5`（路由，可选；若坚持零依赖则用 ServeMux）
- `log/slog`、`encoding/json` 等标准库
